# 面试题库优化规范（所有子任务共用）

## 面试官画像（用人标准）
面试官要招的是“有应变能力、能表达清楚、能自己思考新问题新场景”的 Agent / 大模型应用工程师。每道题都要服务于以下三个考察维度：

| 代码 | 维度 | 含义 |
|---|---|---|
| `pro` | 专业能力 | 技术方向与深度：原理、正确性、工程边界、为什么这样做 |
| `exp` | 表达能力 | 能否把项目/方案讲清楚：结构化、先结论后细节、数据有口径和基线、分清个人贡献与团队工作 |
| `ext` | 扩展/应变能力 | 在项目上扩展新问题、深入场景、条件或方案变更后能否重新推导，“知其然还知其所以然” |

## 写作风格
- 简体中文，专业、克制、短句。技术名词保留英文（LangGraph、RRF、EXPLAIN 等）。
- 不编造候选人没写的事实；对简历内容的追问用“你简历写了 X，……”的口吻。
- `points`：恰好 3 条，每条 ≤ 70 字，写“好答案应覆盖的要点”，不是标准答案全文。
- `follow`：1 个深挖追问，≤ 40 字。
- `twist`：情景变更题，≤ 80 字，必须**改变一个条件**（规模、约束、依赖、需求、故障、团队、预算…）并要求候选人说明原方案哪里要改、为什么。格式建议：“若……，……要怎么改？为什么？”。要与 follow 不重复。
- `good`：高分信号，≤ 60 字，面试官听到什么说明候选人强（尤其体现应变/表达）。
- `bad`：风险信号，≤ 60 字，听到什么说明是背概念、表达不清或不会应变。
- 只输出合法 JSON（UTF-8，不要注释、不要尾逗号）。用 Python `json.load` 自检后再结束。

**新增：** 23 NL2SQL 与数据分析智能体；24 知识图谱与 GraphRAG；25 多模态、文档解析与领域微调；26 项目表达与情景应变

## 通用题池题目 JSON 结构
```json
{"category": 23, "question": "...", "points": ["...","...","..."], "follow": "...", "dims": ["pro","ext"], "good": "...", "bad": "...", "twist": "..."}
```
`dims` 第一个为主维度，可 1~3 个。
